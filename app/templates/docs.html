How the generator works

The web application never invents names, addresses or measurements. It validates input, calls the public PostgreSQL function, and displays the returned rows.

Public SQL API

The primary entry point can be called from psql, another service, or this Flask app:

SELECT *
FROM sul.generate_users(
    p_locale_code => 'en_US',
    p_seed        => 12345,
    p_batch_index => 0,
    p_batch_size  => 10
)
ORDER BY row_index;

A single record can be regenerated without generating earlier batches: 

SELECT *
FROM sul.generate_user('de_DE', 12345, 7, 3);

The identity tuple is (locale_code, seed, batch_index, row_index). Batch and row indexes are zero-based. Batch size changes how many rows are returned, not the identity of a row that remains in the batch.

Deterministic randomness

Every field derives a SHA-256 digest from a canonical string: 

locale | seed | batch_index | row_index | field_salt

The first 56 bits of the digest become an unsigned integer v, then u = (v + 0.5) / 256. The result is strictly inside (0, 1). Field salts such as first_name, latitude, height and phone_format keep one field's changes from shifting every other field.

This design does not use random() or setseed() and does not depend on query plan, row order or session state. pgcrypto is required, and migration initialization fails loudly if it is unavailable.

Distribution algorithms

Normal measurements

Height and weight use Box–Muller with two independently salted uniforms: z = sqrt(-2 ln u₁) · cos(2πu₂). Results are clamped to locale/gender-specific plausible bounds. Clamping changes the tails into small point masses at the limits.

Uniform sphere

z is uniform in (-1, 1), longitude is uniform in [-180, 180), and latitude = degrees(asin(z)). This gives a uniform area distribution and avoids the pole bias of a uniform latitude draw.

Weighted lookups

Locale-compatible candidates are ordered by id, cumulative weights are computed in SQL, and the first cumulative value reaching u · total_weight is selected. All tables use a shared schema with a locale_code key.

Coordinates are globally uniform synthetic points. They are intentionally not the real coordinates of the generated street address.

Locales and lookup data

en_US and de_DE are seeded. Adding a locale means inserting records in sul.locales, regions, cities, names, titles, streets, phone formats, email patterns and body statistics — not rewriting a route or a giant SQL branch.

Check coverage directly in PostgreSQL:

SELECT * FROM sul.lookup_coverage;

Generated email addresses use only example.com, example.net and example.org. A deterministic row-number suffix (for example .001) makes addresses unique within a batch while keeping each record reproducible outside batch context.

HTTP and JSON interface

The HTML generator posts to /generate, /next and /previous. A read-only JSON endpoint is also available: 

GET /api/users?locale=en_US&seed=12345&batch_index=0&batch_size=5

The response contains generated users plus timing metadata. There is no arbitrary SQL endpoint. Health reports application, schema and extension readiness without exposing credentials.

Limits and guarantees

ParameterRule
SeedNon-negative 64-bit integer
Batch index0–1,000,000
Row index0–9,999
Batch size1–10,000 in SQL; {{ max_batch_size }} in this web UI
Email uniquenessGuaranteed within a batch; not a global registry
Phone uniquenessNot guaranteed
Address/coordinate relationIndependent by design

The generator is stateless: no generated users are stored. A public deployment should apply rate limits appropriate to its host; arbitrary SQL execution is never exposed.
